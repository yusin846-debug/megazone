개발 경험이 없어도 괜찮습니다. 우리 팀의 에이전트는 프롬프트 한 장 + 출력 형식 한 장 + 테스트 몇 개로 이루어져 있고, 공통 코드는 기술 리드가 미리 깔아 둡니다. 여러분은 “무엇을 어떻게 판단할지”를 글로 쓰고, 테스트로 확인하면 됩니다.

00큰 그림과 담당

회의 녹음이 들어오면 다섯 에이전트가 차례로 판단하고, 마지막 파일 만들기는 규칙 기반 도구가 맡습니다. 각 에이전트는 한 가지 판단만 합니다.

한 번씩 다 만들어 보고 싶다면

담당 에이전트를 끝낸 뒤, 다른 사람의 에이전트에 테스트 2개를 추가해 주세요. 남이 만든 에이전트를 깨뜨려 보는 게 가장 빠른 공부입니다.

01모든 에이전트가 지키는 규칙

이 다섯 가지는 PRD의 요구사항이자, 검증 에이전트가 실제로 검사하는 기준입니다.

  1. 원문에 없는 내용은 만들지 않는다. 담당·기한이 언급되지 않았으면 null로 둡니다. 화면에는 “미정”으로 나옵니다. (FR-03)
  2. 모든 판단에 근거를 붙인다. 근거는 원문 발언(segment_id)으로 연결합니다. 근거가 없으면 화면에 “미확인”으로 나옵니다. (FR-02)
  3. 제작 방향을 대신 정하지 않는다. 에이전트는 회의에서 정한 것을 찾을 뿐, 더 좋은 안을 제안하지 않습니다.
  4. 모르면 사람에게 묻는다. 확신이 낮으면 questions_for_human에 질문을 남깁니다. 질문은 한 문장, 원문 근거 포함.
  5. 정해진 형식(JSON)으로만 답한다. 형식은 팀의 약속(계약)입니다. 바꾸려면 팀 전체가 합의합니다.

모든 에이전트가 함께 쓰는 조각

// 원문 발언 (A1이 만들고, 모두가 읽음) — ERD: Segment
{ "segment_id": "seg_07", "start_ms": 48000, "end_ms": 50600,
  "speaker": "p_han", "text": "우천이면 리스크 크니까 실내로 돌리죠.", "uncertain": false }

// 근거 (모든 판단에 붙음) — ERD: EvidenceLink
"evidence": [ { "segment_id": "seg_07", "relation": "supports" } ]

// 사람에게 묻기 — ERD: HumanTask 의 재료
"questions_for_human": [ { "target": "action_items[0].due_at",
  "question": "‘스튜디오 대관 확인’ 기한이 원문에 없어요. 지정할까요?",
  "evidence": [ { "segment_id": "seg_11" } ] } ]

시간은 저장할 때 밀리초(start_ms), 화면에 보일 때 00:48 형식입니다.

02작업 틀과 폴더

기술 리드가 공통 틀을 먼저 만들어 둡니다. 여러분이 주로 여는 파일은 굵게 표시한 세 가지뿐입니다.

agents/
  decision/                  ← A3 결정·업무 (예시)
    prompt.md                ← 에이전트에게 주는 지시문. 가장 많이 고칠 파일
    schema.json              ← 출력 형식(계약). 팀 합의 없이 바꾸지 않기
    examples/                ← 테스트
      01_basic.input.json
      01_basic.check.json    ← “이건 꼭 나와야 / 이건 절대 안 돼” 목록
      02_reversal.input.json
      02_reversal.check.json
    index.ts                 ← runAgent("decision", input) 한 줄. 거의 안 건드림
lib/
  runAgent.ts                ← AI 호출 · 형식 검사 · 1회 재시도 · 기록 (기술 리드)
  devRunner.ts               ← 개발용 실행기. 나중에 AIR Studio 어댑터로 교체
fixtures/meetings/           ← 가상 회의 5개 녹취록과 정답지 (팀원 A가 관리)

테스트 실행은 한 줄입니다.

npm run agent:test decision          # A3의 모든 테스트
npm run agent:test decision 02       # 02번 테스트만
결과 예시

✗ 02_reversal     ‘오프닝 장소’ 최종값이 "실내" (정답: "스튜디오")
✓ 03_noise        잡담 속 결정 1건 찾음 · 지어낸 담당 0
   토큰 4,812 · 7.3초 · prompt decision@3

AIR Studio와의 관계

지금은 devRunner(개발용 실행기)로 돌립니다. 05_AIR_Integration의 1단계 그대로입니다. 나중에 실행 계층만 AIR Studio로 바꾸고, 여러분의 prompt.md·schema.json은 그대로 씁니다. AIR Studio의 실제 API는 아직 확인 전이라 직접 호출하지 않습니다.

03만드는 순서 7단계

  1. 역할을 한 문장으로 쓴다“나는 회의 원문에서 확정된 결정과 후속 업무를 찾는다.” 두 문장이 필요하면 에이전트를 쪼개야 한다는 신호입니다.
  2. 입력을 눈으로 본다fixtures/meetings/의 녹취록 하나를 직접 읽고, 내가 사람이라면 무엇을 뽑을지 손으로 적어 봅니다. 이게 첫 정답지입니다.
  3. 출력 형식을 확인한다schema.json을 열어 칸 이름과 필수 여부를 봅니다. 아래 에이전트 카드에 예시가 있습니다.
  4. 프롬프트 초안을 쓴다에이전트 카드의 “프롬프트 시작본”을 복사해 prompt.md에 붙이고 우리 말로 다듬습니다.
  5. 테스트 3개를 만든다쉬운 것 1 · 함정 1 · 애매한 것 1. 함정은 카드의 “꼭 넣을 함정”에서 고릅니다.
  6. 돌려 보고 고친다실패하면 프롬프트를 고치고 다시 돌립니다. 한 번에 한 가지만 고치고, 무엇을 고쳤는지 커밋 메시지에 남깁니다.
  7. 완료 기준을 확인하고 올린다카드의 완료 기준을 모두 통과하면 브랜치를 올리고 기술 리드에게 검토를 요청합니다.

04프롬프트 쓰는 법

좋은 프롬프트는 길이보다 구조가 중요합니다. 모든 prompt.md는 이 순서를 따릅니다.

# 역할
한 문장.

# 입력
무엇이 들어오는지 (원문 발언 목록, 이전 단계 결과 등)

# 해야 할 일
1. … 2. … 3. …

# 판단 기준
말투·신호로 구분하는 표 (아래 예시)

# 하지 말 것
- 원문에 없는 담당·기한·이유를 채우지 않는다
- 더 좋은 안을 제안하지 않는다

# 출력
schema.json 형식의 JSON만. 설명 문장 금지.

# 예시
짧은 입력 1개 → 출력 1개

판단 기준은 “말의 신호” 표로

상태회의에서 들리는 말주의
제안“~어때요?”, “~하면 좋겠어요”, “~도 방법이죠”누가 동의해도 정리 발언이 없으면 아직 제안
확정“~로 하죠”, “~로 정리합시다”, “그걸로 가요”, “확정”결정권자(메인 작가·PD)의 정리 발언인지 확인
보류“다음에 다시”, “일단 보고”, “확인하고 얘기해요”재논의 시점·사유가 있으면 함께 기록
폐기“그건 빼죠”, “이번엔 안 하는 걸로”폐기도 기록 대상. 지우지 않는다

가장 흔한 실수

  • “친절하게” 빈칸을 채움 → 담당자를 추측해 넣음. 빈칸은 null이 정답입니다.
  • 설명 문장을 JSON 앞뒤에 붙임 → 형식 검사 실패. “JSON만 출력”을 마지막 줄에 다시 씁니다.
  • 한 번에 여러 곳을 고침 → 무엇 때문에 좋아졌는지 모름.

A에이전트 카드

각 카드에는 입력 · 출력 · 프롬프트 시작본 · 꼭 넣을 함정 · 완료 기준이 있습니다. ERD 이름은 저장되는 테이블입니다.

A1 전사·화자

녹음을 시간·화자가 붙은 원문으로

기술 리드ERD · TranscriptVersion · Segment

역할

음성 인식 도구를 실행하고, 참석자 명단으로 화자 이름을 붙이고, 확신이 낮은 구간을 표시한다. 내용을 고치거나 요약하지 않는다.

입력 → 출력

입력
녹음 파일 참조(임시 링크) · 참석자 후보 목록. MVP는 이미 전사된 텍스트도 허용
출력
segments[] · uncertain_spans[] · unmatched_speakers[]
{ "transcript_version": 1,
  "segments": [ { "segment_id":"seg_01", "start_ms":12000, "end_ms":16400, "speaker":"p_park", "text":"오프닝은 야외에서 가죠. 한강 공원 어때요?", "uncertain":false } ],
  "uncertain_spans": [ { "start_ms":125000, "end_ms":132000, "reason":"발화 겹침으로 화자 구분 불확실" } ],
  "unmatched_speakers": [] }

꼭 넣을 함정

말 겹침두 사람이 동시에 말하는 구간 → 화자 null + 불확실 표시
호칭으로만 등장“PD님이 말한 거” → 명단과 맞추되 확신 없으면 표시
긴 회의4시간 녹음 → 나눠 처리 후 시간 이어 붙이기가 맞는지

완료 기준

  • 모든 발언이 0 ≤ start < end ≤ 녹음 길이
  • 원본 전사는 덮어쓰지 않고, 정정은 새 버전
  • 불확실 구간이 사람 확인 요청으로 이어짐

A2 제작 맥락

안건별 의도와 아이디어가 바뀐 이유

팀원 AERD · DiscussionItem · ItemRevision · EvidenceLink

역할

회의를 안건 단위로 나누고, 각 안건에서 아이디어가 어떤 순서로, 왜 바뀌었는지 기록한다. 확정 여부는 판단하지 않는다 (A3의 일).

입력 → 출력

입력
A1의 segments · 프로그램 규칙(안건 이름 예시)
출력
topics[] — 각 안건의 idea_changes[]
{ "topics": [ { "item_id":"t_opening", "title":"오프닝 장소",
    "intent": null,                          // 의도가 말로 나오지 않았으면 null
    "idea_changes": [
      { "from":null, "to":"야외(한강 공원)", "reason":null, "evidence":[{"segment_id":"seg_01"}] },
      { "from":"야외(한강 공원)", "to":"실내", "reason":"촬영일 오후 비 예보", "evidence":[{"segment_id":"seg_02"},{"segment_id":"seg_03"}] },
      { "from":"실내", "to":"스튜디오", "reason":null, "evidence":[{"segment_id":"seg_04"}] } ] } ] }

프롬프트 시작본

# 역할
너는 방송 제작회의 원문에서 안건별로 아이디어가 어떻게, 왜 바뀌었는지 기록한다.
# 해야 할 일
1. 원문을 안건(오프닝, 게스트, 촬영 장소 등) 단위로 묶는다.
2. 안건마다 아이디어가 바뀐 순서를 from → to 로 적는다.
3. 바뀐 이유가 원문에 말로 나온 경우에만 reason에 적는다. 없으면 null.
4. 모든 변화에 근거 segment_id를 붙인다.
# 하지 말 것
- 확정·보류를 판단하지 않는다. - 이유를 추측하지 않는다. - 더 좋은 안을 제안하지 않는다.
# 출력
schema.json 형식의 JSON만 출력한다.

꼭 넣을 함정

이유 없는 변경“실내 → 스튜디오”처럼 이유가 말로 안 나옴 → reason null
되돌아간 아이디어야외 → 실내 → 다시 야외 검토 → 세 번째 변화로 기록
안건 넘나들기오프닝 얘기 중 게스트 얘기 → 다른 안건으로 분리

완료 기준

  • 가상 회의 5개에서 정답지의 “변경 이유”를 모두 찾음
  • 원문에 없는 이유를 쓴 경우 0건
  • 모든 변화에 근거 1개 이상

A3 결정·업무

제안·확정·보류·폐기를 가르고 담당·기한을 뽑기

팀원 BERD · ItemRevision(status) · ActionItem

역할

A2가 정리한 안건마다 최종 상태를 판단하고, 회의에서 생긴 할 일을 담당·기한과 함께 뽑는다. 담당·기한이 말로 안 나왔으면 null.

입력 → 출력

입력
A1 segments · A2 topics · 참석자 명단
출력
decisions[] · action_items[] · questions_for_human[]
{ "decisions": [
    { "item_id":"t_opening", "status":"confirmed", "value":"스튜디오",
      "evidence":[{"segment_id":"seg_03"},{"segment_id":"seg_04"}], "confidence":0.92 },
    { "item_id":"t_guest", "status":"on_hold", "value":null,
      "hold_reason":"출연료 확인 필요", "revisit":"다음 주 회의", "evidence":[{"segment_id":"seg_14"}], "confidence":0.58 } ],
  "action_items": [
    { "description":"스튜디오 대관 가능 여부 확인", "assignee":"p_choi", "due_at":null, "evidence":[{"segment_id":"seg_11"}] } ],
  "questions_for_human": [
    { "target":"decisions[1].status", "question":"‘게스트 섭외’는 확정인가요, 보류인가요?", "evidence":[{"segment_id":"seg_14"}] } ] }

status 값: proposed 제안 · confirmed 확정 · on_hold 보류 · dropped 폐기 · confidence 0.7 미만이면 질문을 함께 남깁니다.

프롬프트 시작본

# 역할
너는 방송 제작회의에서 확정된 결정과 후속 업무를 찾는다.
# 해야 할 일
1. 안건마다 status를 proposed/confirmed/on_hold/dropped 중 하나로 정한다. (판단 기준 표 참고)
2. 확정은 결정권자(메인 작가·메인 PD)의 정리 발언이 있을 때만 confirmed로 한다.
3. 누가 하겠다고 말한 일은 action_items에 넣는다. assignee·due_at은 원문에 있을 때만 채운다.
4. 확신이 0.7 미만이면 questions_for_human에 한 문장 질문을 남긴다.
# 하지 말 것
- 담당자·기한을 추측하지 않는다. - 폐기된 안건도 지우지 않는다.
# 출력
schema.json 형식의 JSON만 출력한다.

꼭 넣을 함정

정리 발언 없음모두 “좋네요”만 하고 끝 → 확정 아님, 제안 + 질문
담당만 있고 기한 없음“제가 확인할게요” → assignee만, due_at null
보류 같은 확정“일단 스튜디오로 하고 날씨 보죠” → 확정 + 조건 메모, 애매하면 질문

완료 기준

  • 가상 회의 5개에서 중대한 결정 누락 0건 (PRD 통과 기준)
  • 지어낸 담당·기한 0건
  • 보류·폐기도 빠짐없이 기록

A4 문서 구성

검토된 항목을 템플릿 칸에 배치

팀원 AERD · DocumentVersion · DocumentItemLink

역할

템플릿 버전의 규칙에 따라 각 항목을 알맞은 칸에 넣고 문장을 다듬는다. 새 내용을 만들지 않고, 넣을 곳이 없는 항목은 버리지 말고 unplaced에 남긴다. 글꼴·자간 같은 서식은 출력 도구가 한다.

입력 → 출력

입력
A2·A3 결과(사람이 고친 값 포함) · TemplateVersion.rules_json
출력
sections[](칸별 내용 + 사용한 항목 id) · unplaced[]
// 입력: 템플릿 규칙 (제작회의록 v3)
{ "fields": [
  { "id":"opening", "label":"오프닝", "source":"decisions[item=오프닝*]", "rule":"최종안 + 변경 이력 한 줄", "required":true },
  { "id":"actions", "label":"후속 업무", "source":"action_items", "format":"table", "required":true },
  { "id":"pending", "label":"보류", "source":"decisions[status=on_hold]" } ] }

// 출력
{ "sections": [
  { "field_id":"opening", "content":{ "final":"스튜디오", "history":"야외(한강 공원) → 실내(우천 예보) → 스튜디오" },
    "item_refs":["t_opening@rev3"] } ],
  "unplaced": [] }

꼭 넣을 함정

칸이 없는 항목템플릿에 “드론” 칸 없음 → unplaced로, 버리지 않기
미정 값기한 null → 문서에 “미정” 그대로. 날짜를 만들지 않기
템플릿 변경표 → 담당별 묶음으로 규칙만 바뀜 → 내용은 같고 배치만 다른지

완료 기준

  • 모든 문장에 item_refs가 있음
  • 입력에 없는 사실이 문서에 0건
  • 필수 칸이 비면 빈 칸이 아니라 “미정”·“해당 없음”으로 명시

A5 검증

원문과 대조해 누락·모순·추가·불명확 찾기

팀원 BERD · ValidationFinding

역할

완성된 문서를 원문·항목과 비교해 문제를 찾고, 문제마다 어느 단계로 돌려보낼지(route_to) 정한다. 직접 고치지 않는다.

입력 → 출력

입력
A1 원문 · A2·A3 항목 · A4 문서
출력
verdict · findings[]
{ "verdict": "needs_human",             // pass | needs_fix | needs_human
  "findings": [
    { "type":"missing", "severity":"critical", "target":"pending",
      "message":"03:20 ‘게스트 섭외 보류’가 문서에 없습니다.", "evidence":[{"segment_id":"seg_14"}], "route_to":"decision" },
    { "type":"unclear", "severity":"normal", "target":"actions[0].due_at",
      "message":"기한이 원문에 없습니다.", "evidence":[{"segment_id":"seg_11"}], "route_to":"human" } ] }
type뜻보통 route_to
missing 누락원문에 있는 결정·보류·업무가 문서에 없음decision 또는 compose
conflict 모순문서와 원문(또는 항목끼리)이 서로 다름context / decision
added 추가원문에 없는 내용이 문서에 있음compose
unclear 불명확원문만으로 판단이 어려움human

꼭 넣을 함정

일부러 뺀 문서정답 문서에서 보류 1건을 지운 것 → missing으로 잡는지
일부러 넣은 문서원문에 없는 기한을 넣은 것 → added로 잡는지
문제 없는 문서정답 그대로 → pass (괜히 문제 만들지 않기)

완료 기준

  • 심어 둔 문제를 모두 찾음
  • 문제 없는 문서에 거짓 경보 0건
  • 모든 finding에 근거와 route_to

T문서 출력 도구와 오케스트레이터

이 둘은 AI가 아닌 규칙 코드입니다. 기술 리드가 만들지만, 모두가 규칙을 알고 있어야 테스트를 제대로 짤 수 있습니다.

문서 출력 도구

  • A4의 sections를 템플릿 파일(docx 1종)에 넣고, 글꼴(Noto Sans KR)·자간·강조(변경 이력 형광펜)를 규칙대로 적용
  • 서식 검사: 필수 칸 · 날짜 형식 · 참석자 명단에 있는 이름인지
  • 템플릿 출력 형식만 바뀌면 이 단계와 서식 검사만 다시 실행

오케스트레이터 규칙

상황다음 행동
검증 pass실행 “완료” → 작성자 검토. 문서는 여전히 초안 (자동 승인 없음)
검증 needs_fixroute_to 단계부터 재실행 → 문서 구성 → 검증. 단계당 자동 2회까지 (설정 가능)
검증 needs_human · 재시도 한도 도달사람 확인 요청 생성, 실행은 “사람 확인 대기”
사람이 응답응답 값 고정 → 새 입력 버전 → 영향받는 단계부터 새 하위 실행
전사 정정제작 맥락 이후 결과 무효화 후 재실행
결정 정정문서 구성 이후 결과 무효화 후 재실행
외부 서비스 오류재시도 또는 “실패”, 재시작 위치 표시. 결과를 모르는 요청은 다시 보내지 말고 상태 조회

05AI 코딩 도구에 이렇게 시키기

Cursor나 Claude Code 같은 도구에 아래 문장을 그대로 붙여 넣고, [ ] 부분만 바꿔 쓰세요.

① 실패 원인 찾기 (코드는 건드리지 않게)
agents/[decision]/prompt.md 와 schema.json 을 읽고,
`npm run agent:test [decision] [02]` 를 실행한 뒤 실패한 이유를 설명해 줘.
코드는 수정하지 말고, prompt.md 수정안만 diff로 보여 줘.

② 테스트 추가
agents/[decision]/examples 에 '[정리 발언 없이 끝난 안건]' 테스트를 추가해 줘.
입력은 fixtures/meetings/[03_noise].json 의 [seg_20~seg_26] 구간을 쓰고,
check 파일에는 "t_bgm 의 status 가 confirmed 가 아니어야 함"을 넣어 줘.

③ 결과 정리
`npm run agent:test [decision]` 결과를 표로 정리해 줘.
열: 테스트 이름 / 통과 여부 / 실패 이유 / 토큰 / 시간

지켜 주세요

  • lib/ 공통 코드와 schema.json은 혼자 바꾸지 않습니다. 바꿔야 하면 팀 채팅에 먼저 올리기.
  • API 키를 코드나 커밋에 넣지 않습니다. .env.local에만.
  • 실제 사람의 회의 녹음·이름을 쓰지 않습니다. 가상 회의 데이터만.
  • 내 브랜치에서 작업하고, 기술 리드 검토 후 합칩니다.

06완료 체크리스트

  • 역할 한 문장이 prompt.md 맨 위에 있다
  • 테스트가 3개 이상(쉬운 것·함정·애매한 것) 있고 모두 통과한다
  • 가상 회의 5개로 돌렸을 때 지어낸 값 0건
  • 모든 판단에 segment_id 근거가 있다
  • 애매한 경우 questions_for_human이 나온다
  • 프롬프트 버전(@3 등)을 올리고 무엇을 바꿨는지 기록했다
  • 다른 사람 에이전트에 테스트 2개를 추가했다 (선택)
